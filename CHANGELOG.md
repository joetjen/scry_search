# Changelog

## [Unreleased]

### Added

- Initial project scaffold: `mix.exs` (app `:scry_search`, `{:scry_core, path: "../scry_core"}` + direct `ichor`/`ichor_runtime` dependencies since this package does its own grammar parsing/analysis/dispatch, matching every other kind package's own precedent), `.credo.exs`/`.formatter.exs`/`.tool-versions`, `AGENTS.md`/`CLAUDE.md`.
- `priv/grammar.aether`: fills `comparison_ep1e`, `scry_core`'s new third extension point (EP1(e), added specifically to make this package possible -- see that package's own `CHANGELOG.md`), with lang_spec.md §8.5's `<field> SEARCH <string>`. `left:predicate_lhs` is core's own dangling reference, reused verbatim (the same three shapes, `call_with_path | call | path`, any other comparison's own left-hand side already accepts); `right:STRING` deliberately, not `literal`/`path` -- `SEARCH`'s own right-hand side is always a fuzzy-match query string. `relevance()` needed no grammar contribution at all -- an ordinary bare call already parses through core's own generic `call` production (the same finding that resolved `scry_time_series`'s own `rate(<duration>)`).
- `Scry.Search.Actions`: owns `comparison_ep1e`, delegates every other rule/token to `Scry.Core.Actions` (the same delegation-not-composition shape every other kind package already establishes). **The one genuine difference from every EP1(b)/(c)/(d) kind package built so far**: `comparison` (the host production `comparison_ep1e` extends) has no equivalent wrapping clause the way `body_item` does for `body_item_ep1` (confirmed directly: `Scry.Core.Actions.handle_rule/3` has exactly four `:comparison` clauses, none matching a bare `%{comparison_ep1e: _}` capture), so this module's own `comparison_ep1e` handler does the `{:variant, {:search, left, needle}}` wrapping itself.
- `priv/gen/generate_compiled_grammar.exs`: produces the checked-in `Scry.Search.Grammar.Compiled`, mirroring every other kind package's own generator exactly.
- `Scry.Search.parse/1`: mirrors `Scry.Core.parse/1`'s own shape, using the merged grammar and `Scry.Search.Actions`.
- **`Scry.Search.Executor`** -- implements `Scry.Core.EngineBehaviour` directly, the first kind package to double as its own engine rather than requiring a real storage adapter underneath it (see this package's own `README.md` for the full "why" -- `SEARCH` needs to inspect real row data, unlike `scry_time_series`'s pure-AST `LAST` lowering or `scry_document`/`scry_graph`'s `select`-body-structure executors). No bespoke `Conn` module -- `conn` is the same plain `%{[String.t(), ...] => [row]}` map every in-memory reference engine in this ecosystem already uses, since `SEARCH` needs no new storage primitive, only new execution logic.
  Walks `query.wheres` recursively (through `AND`/`OR`/`NOT`), extracting every `{:variant, {:search, left, needle}}` leaf and replacing each with an ordinary boolean-field comparison; for each of the source's own rows, computes each extracted clause's own toy token-overlap score (lowercase, tokenize on non-letter/non-digit boundaries, count of needle tokens also present in the field's own tokens) and merges it onto the row as that clause's own match flag plus a running `relevance()` total; rewrites every `{:call, "relevance", []}` in `select`/`order_bys` to reference that total; hands the rewritten query and annotated rows to `Scry.Core.QueryOps.run_flat/3`. Composes for free with `GROUP BY` (matching happens per-row, before grouping, unlike `scry_document`/`scry_graph`'s own pseudo-fields, which needed a real `GROUP BY` scope limit) and with `WITH` bindings (resolved directly, recursing into this module's own `run/3` for the bound query, since `Scry.Core.QueryOps.run_document/4`'s own `resolve_source/5` calls `run_flat/3` directly once a binding resolves, bypassing `execute/3` -- confirmed by reading it, not assumed).
  Two stated scope limits, returned as clear `{:error, {:unsupported, {:construct, ...}}}` rather than silently mishandled: `SEARCH` anywhere in `HAVING` (`:search_in_having` -- a per-row match doesn't obviously aggregate across a group, and lang_spec.md's own single worked example never uses it there), and a `SEARCH` left-hand side that isn't a bare field path (`:search_lhs_not_a_field` -- `predicate_lhs`'s other two shapes parse fine but aren't resolved here), checked before any row is touched, not raised deep inside per-row scoring.
- `test/scry/search_test.exs`/`test/scry/search/grammar_parity_test.exs`: grammar/parse coverage for `SEARCH` (bare, case-insensitive, combined with `AND`/`OR`/`NOT`), `relevance()` as a plain computed field and in `ORDER BY`, and the lang_spec.md §8.5 worked example.
- `test/scry/search/executor_test.exs`: real execution coverage -- the worked example end to end, the toy scorer's own exact arithmetic (including a property-based test against a naive word-set-intersection reference, per this project's own `AGENTS.md` stream_data guidance), `GROUP BY` composition, `WITH`-binding composition, a correlated nested `SELECT`, a `UNION` across two `SEARCH`-filtered sources, and both stated scope limits.

### Fixed (via `scry_core`, not this package -- included here since they were found building it)

- Four real gaps in `scry_core`'s own predicate-tree walkers, every one written before `comparison_ep1e` existed and none with a catch-all for the new `{:variant, ...}` leaf: `Scry.Core.QueryOps.streaming_predicate_calls/1`, `predicate_has_aggregate_call?/1`, `rewrite_predicate_correlation/4`, and all three of `Scry.Core.TypeCheck`'s own walkers (`walk_type_check/3`, `walk_json_check/2`, `check_predicate/4`) -- the last three meant parsing *any* query using `SEARCH` crashed with a raw `FunctionClauseError`, unconditionally, with no `TYPE` declaration involved at all. See `scry_core`'s own `CHANGELOG.md` for each fix.
